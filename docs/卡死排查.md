# 程序偶发卡死（界面无响应）排查评估报告

> 现象：程序有时整个窗口卡死、界面点不了；据反馈，卡死时用户**基本没做操作，最多切换标签页**。
> 本文是纯静态代码审计的结论（未改任何代码、未运行复现），列出可能的根因、证据位置、
> 已排除项、未覆盖项、优化方案，以及一份"如何逐条核实"的清单。
>
> 审计日期：2026-11-27　基线：`main` @ `328aff59`

---

## 0. 结论摘要

代码库整体工程素质很高：主循环稳态路径几乎全部异步化，消息泵每帧都有"条数 + 毫秒"预算
（`message_handler/*.rs` 里的 `MAX_*_PER_FRAME` / `*_BUDGET_MS`），文件操作通道无界、进程回收用
`try_wait`、退出路径有 5 秒看门狗。因此卡死**不是普遍性问题**，而是若干**特定触发条件下的
UI 线程阻塞**。

结合"空闲 / 切 tab"这条线索，根因可能性排序：

| 排序 | 根因 | 典型场景 | 预估阻塞 | 验证状态 |
|---|---|---|---|---|
| ① | 切换标签页时 UI 线程**同步访问搜索服务命名管道** | 搜索服务忙碌/建索引/USN 追赶时切 tab | 忙等 0.9 s + 响应超时 2 s ≈ **1–3 s/次** | 亲自验证 |
| ② | **文本预览**：整段文本每帧重新排版 + 首次预览同步整读文件 | 某个 tab 里选中过 .txt/.log/.csv/.md（几百 KB–2 MB 最糟） | 每帧数百 ms–数秒，**停在该 tab 期间持续卡** | 亲自验证 |
| ③ | **后台驱动的文件监视/云同步事件风暴**（UI 线程 O(N) 扫描） | 空闲时 OneDrive/下载器/构建等在当前目录写文件 | 单帧数百 ms，连续多帧 | 子代理验证，本人抽查属实 |
| ④ | **缩略图库 VACUUM 持锁期间 UI 阻塞拿同一把锁** | 批量删文件后最小化再恢复 | 数十秒到分钟级 | 子代理验证 |
| ⑤ | 空闲时**工作集修剪**后的缺页风暴 | 特定 GPU 内存策略下空闲数秒后的首次重绘 | 0.5–3 s 顿挫 | 亲自验证（条件性） |
| ⑥ | 其他 UI 线程同步 I/O（地址栏/终端/驱动器/归档判定/剪贴板/mpv 关闭） | 见第 5 节 | 数百 ms–数十秒 | 子代理验证 |

> 时间线提示：文本预览的"全量加载"是 `13b74ca0`（2026-11-21）引入的（之前是 256 KB 截断）。
> 如果卡死是 11-21 之后才明显变多，② 基本可以锁定。
>
> **2026-11-27 补充（重要）**：用户确认卡死是**永久性**的（等多久都不恢复，只能杀进程）。
> 这一条改变了优先级：上表 ①②③ 都能解释"卡住数秒到数十秒但通常会自行恢复"的现象，
> 但**都解释不了永久卡死**——文本预览每帧慢，但事件循环仍在推进（点击会被处理，只是很慢）；
> 管道往返最多约 3 秒就超时返回；事件风暴会随积压清空而恢复。永久卡死意味着 UI 线程在等
> 一个**永远不会完成**的东西：死锁、无超时的系统调用、或 GPU present 无限等待。
> 针对永久卡死的分析、证据与核实方法见 **第 10 节**。

## 1. 审计方法与局限

- 范围：`src/` 约 26 万行（1241 个文件）+ `crates/`。先用模式扫描定位（`recv/sleep/join/lock/set_fonts/
  load_texture/std::fs/Win32 Shell API` 等），再对 UI 线程每帧入口做调用链精读。

  → `process_incoming_messages`（`src/app/operations/message_handler/`）→ 各 layer → `render_panels`

  `sleep/recv/join` 属正常。
- 本机未开启诊断模式、没有历史日志，所有结论来自静态分析，**没有运行时证据**；第 8 节给出核实方法。

## 2. 根因 ①：切换标签页 → UI 线程同步命名管道往返（亲自验证）

### 2.1 调用链

| 跳 | 位置 | 说明 |
|---|---|---|
| 1 | `src/app/operations/tabs.rs:359`（`sync_from_tab`）、`src/app/operations/panel_tab_ops.rs:83`（`restore_panel_tab_snapshot`） | 用户切换 tab 时在 **UI 线程**调用 `tab_path_staleness` |
| 2 | `src/app/operations/tabs/staleness.rs:21-33` | `global_search.available` 为真时直接调用 `global_search::check_paths_modified(&[path], 120)`；第 29 行的日志文本自己写着 "skipping UI-thread mtime fallback" |
| 3 | `src/infrastructure/global_search.rs:179-206` `check_paths_modified` | `open_pipe()?` → `write_message` → `read_validated_response(pipe, CHECK_PATHS_TIMEOUT_MS)`，全部同步 |
| 4 | `src/infrastructure/global_search.rs:338-395` `open_pipe` | `CreateFileW` 打开管道；`PIPE_BUSY` 时 `sleep(150ms)`，最多 6 次（第 344-345 行）；打开成功后**每次**调用 `verify_server_process` |
| 5 | `src/infrastructure/global_search.rs:417` `verify_server_process` | `GetNamedPipeServerProcessId` + SCM 查询（`OpenSCManagerW/OpenServiceW/QueryServiceStatusEx`，RPC；控制台模式还会 `CreateToolhelp32Snapshot` + 进程路径 `canonicalize`）。SCM 部分由子代理确认 |
| 6 | `src/infrastructure/global_search.rs:160`、`:19` | `CHECK_PATHS_TIMEOUT_MS = 2_000`，读响应用 `PeekNamedPipe` + `sleep(15ms)` 轮询 |

### 2.2 阻塞时长

- 服务空闲：几 ms 到几十 ms（感知不到）。
- 服务**所有管道实例都忙**（建索引、大查询、USN 追赶）：先忙等 6 × 150 ms = 900 ms。
- 服务**收到请求但处理慢/假死**：再等满 2000 ms 超时。
- 合计最坏 ≈ 3 s，**每切一次 tab 重复一次**；若服务持续假死，表现为"切 tab 就卡"。

### 2.3 设计错位

`open_pipe` 第 341-343 行注释："fail immediately instead of blocking the worker thread for seconds"
——这套客户端是为**工作线程**设计的（搜索、盘健康、文件夹大小等调用点确实都在 worker），
只有 tab 新鲜度检查这一处把它搬到了 UI 线程。

### 2.4 修复方向

- `tab_path_staleness` 改为异步：先返回 `(false, false, false)`，把请求投给 `global_search_worker`，
  结果回来后再把 tab 标为 stale（tab 上本来就有 stale 标记的渲染路径）。
- `verify_server_process` 的 SCM 查询按 server PID 缓存（例如 10 s），不必每次开管道都做。
- 在 `global_search.rs` 的同步入口加注释/断言，禁止 UI 线程调用。

## 3. 根因 ②：文本 / Markdown 预览（亲自验证）

### 3.1 同步整读文件

| 位置 | 说明 |
|---|---|
| `src/ui/preview_panel/text_preview.rs:128-129` | `render_text_preview`（预览面板渲染，UI 线程）每帧调 `cached_text` |
| `src/ui/preview_panel/text_preview.rs:72-93` `cached_text` | egui 临时数据缓存未命中时，在 `ctx.data_mut` 闭包内**同步**调用 `load_text`（第 83 行），结果 `insert_temp`（第 90 行） |
| `src/ui/preview_panel/text_preview.rs:412-449` `load_text` | 第 413 行 `std::fs::read(path)` **全量读取、无大小上限**（注释 "No truncation: big files load in full"）；第 436 行 `decode`（含 chardetng 编码探测）；第 437-438 行超过 2 MB 再 `build_virtual_lines` |
| `src/ui/preview_panel/markdown_preview.rs:176` | Markdown 预览复用同一个 `cached_text`，问题相同 |

对比：同目录的 SVG/PDF/DOCX/XLSX/图片预览全部是"后台线程 + `try_recv`"模式
（如 `svg_preview.rs:27-38`），只有文本是例外。

### 3.2 小文件路径每帧重新排版

`src/ui/preview_panel/text_preview.rs:157-187`：

- `> 2 MB`（`VIRTUAL_THRESHOLD_BYTES`，第 41 行）→ `render_virtual_text`，只排可见行，没问题。
- `≤ 2 MB` → 第 164 行 `cached_expanded_text`（再缓存一份 Tab 展开后的全文副本，第 193-203 行）
  → 第 165 行 `highlighted_job` → 第 166-186 行 `ScrollArea::both().show` 里把**整段文本作为一个
  `egui::Label`**。egui 的 galley 缓存是按帧的，`Label` 每帧重新分词、排版、三角化全部字形。

代价估算（估算，未实测）：200 KB ≈ 每帧几十 ms（掉帧）；1 MB ≈ 每帧数百 ms 到 1 s+；
2 MB ≈ 每帧数秒——窗口仍在"运行"，但每次点击要等好几秒才被处理，正是"界面都点不了"的体感，
而且因为卡住很难切走。

### 3.3 内存驻留

`insert_temp` 的生命周期与 `egui::Context` 相同，没有淘汰：每个预览过的文本文件全文
（`CachedText` + Tab 展开副本）都常驻内存。预览过几个大日志后内存持续膨胀。

### 3.4 引入时间

- `6ed66210` 2026-11-20：文本预览，256 KB 截断。
- `13b74ca0` 2026-11-21：去掉截断、改为"全量加载 + 虚拟化"（只虚拟化了 > 2 MB 的部分）。

### 3.5 修复方向

1. 读取移到后台线程：照搬 `svg_preview.rs` 的 `in_flight: Mutex<Option<Receiver>>` + `try_recv` 模式，
   未就绪时显示"加载中"。
2. 加大小上限（例如 64 MB，超出直接提示"文件过大，请用外部编辑器打开"），杜绝 GB 级整读。
3. 小文件路径也走 `render_virtual_text`（阈值从 2 MB 降到约 64 KB），彻底消灭整段 `Label`。
4. 缓存改 LRU（例如 8 条或按字节上限），切走后释放。

### 4.3 修复方向

- 为 `all_items` 建立 normalized 路径 → 下标的 `HashMap`（按 generation 失效），把 4.1 表中的全部
  O(N) 扫描降为 O(1)；Create 事件 50–100 ms 去抖合并后只 `rebuild_group_projection` 一次；
  事件处理增加"包含消息内部"的每帧总预算，超预算续排 `request_repaint`。
- `is_network_or_virtual` 先 `GetDriveTypeW`，卷信息按盘符缓存（如 30 s），网络盘直接短路。
- 自动 GC 不做 VACUUM（或改 `PRAGMA incremental_vacuum` 并在独立连接/锁外执行）；UI 线程所有
  DB 写改 `try_lock`，失败即入队给现有 `disk-cache-invalidation` 线程；`LIKE` 改范围查询
  （`path >= p AND path < p || x'01'`）；`db_utils` 显式 `busy_timeout(250ms)`。

## 10. 永久卡死补充分析（2026-11-27）

### 10.1 什么样的原因能造成"永久"卡死

UI 线程必须停在下面某一类**不会自行返回**的等待上：

| 类别 | 机制 | 特征 |
|---|---|---|
| A. GPU present 无限等待 | DX12 合成器 swapchain 等"合成器给出的帧"；窗口被遮挡/最小化/显示器休眠/锁屏/独占全屏/RDP 切换时，合成器可能永不再送帧，`Present` 内的帧延迟等待对象永不置位 | CPU 0%，窗口"未响应"，日志停在 `stage=ui_end` 之后（新增看门狗可证实） |
| B. 无超时的系统调用挂在过滤驱动/网络 | `GetFileAttributesW`/`GetVolumeInformationW`/`fs::read` 等落在挂起的云盘占位文件（OneDrive `cldflt`）、Cryptomator/Dokan/WinFsp、断连 SMB、休眠 USB 上；过滤器驱动可以把请求永久挂起 | CPU 0%，栈在 `NtDeviceIoControlFile`/`NtCreateFile` |
| C. 锁/通道死锁 | 两线程互等：UI 线程等锁；持锁线程等 UI 线程才能推进的资源（有界通道、事件、回调） | CPU 0%，永久 |
| D. 原生模态循环不退出 | `TrackPopupMenu`/`MessageBox`/`DoDragDrop` 进入模态循环且从未被关闭（例如 owner 窗口被隐藏） | 通常能看到菜单/对话框；若 owner 不可见则像死机 |

### 10.2 本项目里指向 A 类的证据（最可疑）

- `src/main.rs:261`：显式设置 `presentation_system = Dx12SwapchainKind::DxgiFromVisual`
  —— DX12 走 DirectComposition visual，不是普通 HWND swapchain。
- `src/gpu_backend.rs:18`：Windows 上默认后端**只有 DX12**；用户没改设置就一定是这条路径。
- `src/main.rs:754-756`：`with_transparent(true)`，注释说明"透明需要 alpha-capable GPU 配置，
  由主窗口与浮动预览共享"——透明正是必须用 Composition swapchain 的原因。
- `vendor/winit` 的两个补丁：`954e4862`（DX12 退出时**隐藏窗口**）、`4411daab`（DPI 拖动补丁）
  ——都在处理"窗口状态切换 + DX12"的问题；`tools/dx12-present-test` 专门测
  `--hwnd` / `--visual` 两种呈现方式 × 三种最小化流程（winit / `ShowWindow` / GDI+DWM 预览），
  说明这个方向曾经踩过坑。
- `src/main.rs:742-744`：注释明确写着"force-kill on exit to avoid the **OneDrive/cldflt
  zombie-process hang**"——项目已经遇到过 B 类（过滤驱动挂起），所以 B 类同样不能排除。

A 类与用户描述的"我什么都没做，最多切个 tab"非常吻合：显示器休眠、锁屏、远端桌面断开、
切到全屏游戏/视频、甚至 DWM 重启，都会让合成器停止供帧；此时后台线程照常跑，
但 UI 线程永远停在 `Present` 上。

### 10.3 已排除的"伪永久"

| 项 | 排除理由 |
|---|---|
| 缩略图库 VACUUM 持锁 | 本机 `thumbnails.db` 仅 6 MB（`%LOCALAPPDATA%\MTT-File-Manager\thumbnails\`），VACUUM 毫秒级；且只有最小化 + 本会话删除 ≥ 8000 条才触发 |
| 切 tab 的搜索管道往返 | 有界：忙等 6×150 ms + 读取超时 2000 ms，最坏约 3 秒后返回错误 |
| 文本预览整段排版 | 每帧慢（数百 ms–数秒），但事件循环在推进、输入最终会被处理；且切走即恢复 |
| 监视/云同步事件风暴 | 每帧有 50 条上限 + 5 ms 预算，积压清完后恢复 |
| 退出路径 join/sleep | `handle_exit` 有 5 秒看门狗强杀 |
| 文件操作 / 缩略图通道满 | 预览请求全用 `try_send`；文件操作通道 unbounded |

### 10.4 已加入的“卡死看门狗”（本次改动）

新增 `src/ui/app/stall_watchdog.rs`，并在 `logic()`、`ui()`、消息泵的关键边界插入了阶段标记：

- UI 线程每进入一个阶段就更新一个原子心跳；后台 `ui-stall-watchdog` 线程每秒采样。
- 心跳 5 秒未推进即写日志（同时写 `log::error!` 与
  `%LOCALAPPDATA%\MTT-File-Manager\logs\stall.log`，不依赖诊断模式、不依赖日志系统是否可用）。
- 记录内容：卡住时长、**最后到达的阶段**、帧计数、进程 CPU 占用（0% = 在等待，100% = 在空转）。
- 心跳恢复时写一行 `[STALL-RECOVER]`，便于区分"卡了一下"和"永久卡死"。

阶段判定表：

| `stall.log` 里的 `stage=` | 说明 | 对应根因 |
|---|---|---|
| `ui_end` | `ui()` 已返回，阻塞发生在其后（present / winit 事件循环） | **A 类（DX12 present）** |
| `logic_start` / `logic_end` | 阻塞在 `logic()` 内（启动序列、托盘事件、标签页传输、外部打开） | 需看具体是哪个子调用 |
| `messages` / `file_operation_results` / `watcher_events` / `streaming_thumbnails` | 阻塞在消息泵的对应子阶段 | B 类系统调用 / C 类锁 |
| `panels` | 阻塞在面板渲染（预览面板：文本预览同步读文件、图片/PDF 预览） | B 类（慢盘/云盘）或文本预览 |
| `context_menu` / `settings_window` / `overlays` | 阻塞在右键菜单（Shell 扩展）、设置窗口、全局搜索浮层 | Shell 扩展挂起 |
| `ui_minimized_skip` | 最小化分支后卡住 | 基本只可能是 present |

### 10.5 下一步核实（按成本从低到高）

1. **零改动实验**：设置 → 后端 → 切到 **Glow（OpenGL）**，正常使用几天。若永久卡死消失，
   A 类（DX12 合成器 present）基本坐实。这是最快、最有判别力的实验。
2. **看 CPU**：下次永久卡死时看任务管理器里 `mtt-file-manager.exe` 的 CPU：
   接近 0% → A/B/C；持续 100% → 一定是代码里的死循环（届时再查）。
3. **看看门狗日志**：编译本次改动后，卡死时直接看 `logs\stall.log` 最后一行，按 10.4 的表判读。
4. **场景关联**：记录卡死前是否发生——显示器休眠/锁屏/远程桌面/全屏游戏或视频/拔插显示器/
   OneDrive 大量同步/访问网络盘或 Cryptomator 目录。
5. 若日志显示 `stage=ui_end` 且确认与遮挡/休眠有关：修复方向是去掉 Composition swapchain
   （改 `DxgiFromHwnd`，代价：整体透明需要改为"仅浮动预览窗口透明"），或在不可见期间
   停止请求重绘（`request_next_background_repaint` 在隐藏/最小化时不发 repaint，
   改由工作线程完成必要工作）。若日志显示 B 类：把那处调用移到工作线程并加超时。
